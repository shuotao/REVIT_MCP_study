# 相機管理面板 決策紀錄（ADR）

> 格式：背景 → 決策 → 理由 → 後果。編號只增不改；被取代的決策保留原文，標「已被 D-xxx 取代」。
> 來源：舊版規格書 `docs/camera-manager-spec.zh-TW.md` 內的決策註記、`log/2026-09.md` 2026-09-24～25 相機管理條目、本分支 commit。
> 現行行為見 [spec.zh-TW.md](spec.zh-TW.md)。

## D-001 做成 Revit 原生停靠面板，不做 MCP App、不把面板功能 MCP 工具化（2026-09-24，使用者拍板）

- **背景**：需求是「讓使用者清楚定位每台相機並能調整、出圖」。可選路徑有 MCP App（`ui://` 網頁）、MCP 工具、Revit 原生 WPF。
- **決策**：做成 Revit 內的原生視窗；不走 MCP App，也不把面板操作做成對話式工具。
- **理由**：使用者要在 Revit 裡邊看邊調；原生視窗能直接用 Revit API 事件做雙向連動、能開 Revit 視圖並排，MCP App 做不到這些，而且要先有 AI 用戶端連線才能用。
- **後果**：面板與 MCP 伺服器的工具數無關；Revit API 呼叫要自己處理 ExternalEvent 與執行緒。後來為了自動測試另加 MCP 測試工具（D-023），但那是測試通道，不取代面板。

## D-002 無模式浮動視窗改成停靠面板（2026-09-24）

- **背景**：第一版是無模式 WPF 視窗，容易被主視窗蓋住、每次要重開。
- **決策**：改用 `RegisterDockablePane`，UI 拆成可替換的 UserControl，Revit 讀寫集中到不含 WPF 型別的 `CameraManagerService`。
- **理由**：停靠面板跟 Revit 其他面板一樣可固定、記住位置；讀寫與 UI 分開，第 2 階段加功能不必動 WPF。
- **後果**：受停靠面板宿主環境限制（透明背景畫黑、鍵盤焦點被主視窗搶），衍生 D-006、D-009。

## D-003 面板上所有高度一律用「離樓板高度」（2026-09-24）

- **背景**：性質面板的 Eye Elevation 從內部原點量起，實測專案 1F 上方 175 cm 的相機顯示負值。
- **決策**：清單與編輯一律用「眼睛 − 下方樓層高程」；Eye Elevation 原始值只以唯讀選用欄位顯示。
- **理由**：設計師以樓板為基準思考人視高；原始值的 0 點看不出來。
- **後果**：沒有下方樓層的相機無法編輯（清單顯示「找不到樓層」）。

## D-004 Key Plan 用真的 Revit 視圖，不自己畫圖（2026-09-24，使用者拍板）

- **背景**：Key Plan 可以是面板內自繪圖，也可以是 Revit 平面／剖面／3D 視圖。
- **決策**：一鍵 4 視圖建立真的 Revit 平面、剖面、等角視圖，並與透視圖並排。
- **理由**：真視圖可直接拖剖面線、可排上圖紙列印、同事開檔也看得到；面板自繪圖做不到。
- **後果**：要處理視圖樣板繼承、類別可見性、比例、裁剪框等 Revit 表現問題（D-016、D-014 等）；視圖名稱含「Key Plan」。

## D-005 視圖與相機用 Extensible Storage 連結，不靠名稱（2026-09-24）

- **背景**：以名稱找 Key Plan 視圖，相機一改名就變孤兒、重跑會生出重複視圖。
- **決策**：ES Schema `RevitMCP_CameraKeyPlanLink`（`CameraUniqueId`＋`Role`）記在視圖與標記元素上；找不到才退回精確名稱比對。
- **理由**：UniqueId 跨工作階段穩定；同一份 Schema 也可標記「自己畫的標記」，重跑時只刪自己的東西。
- **後果**：GUID 與欄位定義一經發佈不可改；新需求要開新 Schema（見 D-015）。

## D-006 主題採 palette B「天空藍卡片」，集中在單一主題檔（2026-09-24，使用者從三份 mockup 選定）

- **背景**：停靠面板宿主在透明 WPF 背後畫黑，面板整片變黑。
- **決策**：`CameraManagerTheme.cs` 為色彩／字型／間距／圓角唯一正本（背景 `#F3F7FC`、accent `#3B82C4`…），每層容器都給顯式背景。
- **理由**：修掉黑底；單一正本避免各元件各自寫色碼。
- **後果**：所有新元件必須從主題檔取 Brush／Style。

## D-007 不用分頁，單頁 ①–⑥、無外層捲軸（2026-09-24，使用者拍板）

- **背景**：曾做過藥丸形四分頁（相機／位置圖／細節／工具），切換麻煩且資訊被拆散。
- **決策**：拿掉分頁，單頁固定順序①工具列②清單③位置圖④視圖操作⑤人視高⑥狀態列；拿掉「選取中相機」卡片，欄位移進清單選用欄；③ 吃剩下高度；次要功能收進「⋯」選單。
- **理由**：窄面板內一眼看到清單與地圖；區號讓使用者能用名稱指稱。
- **後果**：`PillTabControl.cs` 保留但不再組裝；空間緊，新增控制項優先放進選單。

## D-008 面板懶載入＋專用事件佇列（2026-09-24，兩輪崩潰後）

- **背景**：開檔後 5–10 秒無操作崩潰（`0xe0434352`）。查到：共用 `ExternalEventManager` 只有一個動作欄位、連排會互相覆寫且會跳 TaskDialog；開檔期間事件就觸發讀取與匯出。後來 crash log 實證直接起因是樓層欄 ComboBox 套到 TextBlock 樣式。
- **決策**：面板開檔不讀、不匯出、不畫，等使用者按「重新整理」；面板改用自己的 FIFO `CameraManagerEventQueue`（不丟動作、不跳對話框）；Revit 物件攤平成 double 才交給 WPF；UI 回呼一律非同步；加上必定留下堆疊的崩潰診斷。
- **理由**：把「開檔當下」的所有面板工作拿掉，讓崩潰面縮到使用者主動操作；診斷確保下次有堆疊可查。
- **後果**：第一次使用要按一次重新整理；面板與 MCP 命令不共用佇列（MCP 測試工具走 MCP 自己的 ExternalEvent，見 D-023）。

## D-009 清單編輯改成常駐控制項，不走 DataGrid 編輯模式（2026-09-25，第三次修正）

- **背景**：「雙擊進編輯」被雙擊跳轉搶走；改「單擊 BeginEdit」兩輪實機仍失敗，log 完全沒有編輯紀錄＝DataGrid 從未進入編輯模式（Revit 主視窗搶焦點、live sync 換 ItemsSource）。
- **決策**：DataGrid 全唯讀，可編輯欄的儲存格內直接放常駐 TextBox／ComboBox；Enter／失焦提交、Esc 還原；名稱欄改成單擊＝一鍵 4 視圖，重新命名移到右鍵選單。
- **理由**：不依賴 DataGrid 的編輯握手，焦點就在 TextBox 上。
- **後果**：清單重建要避開有焦點的儲存格（延後重建）；log 追蹤按鍵是否送達。

## D-010 改樓層＝複製相機，不就地換樓層（2026-09-25，使用者決策）

- **背景**：同日先做了「就地換樓層＋退役舊樓層 Key Plan 平面」，會改動既有相機與視圖。
- **決策**：清單樓層欄選另一個樓層時，沿用「複製到其他樓層」在該樓層複製一台新相機；原相機與其 Key Plan 完全不動。
- **理由**：換樓層通常是「同位置在另一層也要一台」；不破壞既有相機與已排圖的視圖。
- **後果**：取代同日「就地換樓層」版本；新相機需要時再按一鍵 4 視圖。

## D-011 等角視圖為真正的標準等角（2026-09-25，第六輪）

- **背景**：先後試過固定 TOP-BACK-LEFT 角（不隨相機）、再改成「相機精確 yaw 往下俯 35.26°」——後者不是標準等角，畫面看起來歪。
- **決策**：在 ViewCube 上方四角中挑水平方向最接近相機者，forward＝(±1, ±1, −1)/√3。
- **理由**：兼顧「從相機那一側看」與「標準等角外觀」。
- **後果**：相機轉動 90° 以內等角方向不變；跨象限才換角。

## D-012 Key Plan 範圍以「眼睛所在房間」為主，並分室內／室外兩套規則（2026-09-25）

- **背景**：沿視線取樣房間會穿牆進到鄰戶（實測框到 4 個房間、剖面 20 m）；室外相機套「無房間 → 夾 8 m」後範圍太小。
- **決策**：先判定室內／室外。室內＝眼睛所在房間 +0.6 m、房間頂為主（挑高與夾層）；室外＝視野扇形（半徑 min(遠裁剪, 室外半徑，預設 60 m)），等角 Z 由範圍內模型最高點決定、不做樓層切。
- **理由**：使用者：「以我們這間房間為主，往外留一些 buffer」；室外沒有房間可依。
- **後果**：室外半徑成為使用者設定；房間邊界錯誤會直接影響範圍。

## D-013 剖面方向預設「對齊房間長邊」，並通過畫面中心（2026-09-25，使用者拍板）

- **背景**：沿視線的剖面常斜切房間，不易讀。
- **決策**：預設對齊房間長邊（最小面積外接矩形），另可選「沿視線」；室外一律沿視線。剖切線通過畫面中心線（非對稱視錐的角平分線）上半個扇形半徑處。
- **理由**：剖面與房間正交最好讀；通過可見範圍中心，剖面才代表畫面裡看到的東西。
- **後果**：剖面不一定包含視線，標記要投影到剖面平面；ES 剖面狀態改記實際原點。

## D-014 剖面樓層改畫「簡化樓層記號」並同步真樓層（2026-09-25 第二版，使用者拍板）

- **背景**：樓層標頭白底蓋住內容；剖面中大量近同高程樓層與**連結模型**樓層（主體無法逐元素隱藏連結內的元素）。先試過逐元素隱藏、視圖專屬 2D 範圍伸出框外，都無法處理連結樓層；6 個連結都已是「依主體視圖」仍會顯示連結自己的樓層。
- **決策**：淡化樣式下剖面整類隱藏樓層，改畫詳圖線＋TextNote 的簡化記號，以 ES 連結真實 Level，Level 改動時自動重畫。
- **理由**：使用者要看得到樓層、又不能被蓋住，且日後改樓層要同步；自畫記號才同時滿足三點。
- **後果**：記號不是 Revit 樓層，不能拖曳改高程；剖面文字類別改逐元素隱藏。

## D-015 保留使用者手動調整過的剖面，另給「重設剖面位置」（2026-09-24）

- **背景**：重跑一鍵 4 視圖會把使用者拖過的剖面蓋回去。
- **決策**：新 ES Schema 記下程式產生時的原點與方向，偏差 > 5 mm 或 > 2° 就不覆寫；「重設剖面位置」強制覆蓋。
- **理由**：尊重手動調整；不改既有 `CameraKeyPlanLink` Schema（D-005 後果）。
- **後果**：第一版 Schema 的 double 欄位沒設單位，`SchemaBuilder.Finish()` 失敗導致整筆交易回滾；已換新 GUID（`RevitMCP_CameraSectionStateV2`）並加單位。

## D-016 淡化背景用類別／元素取代，而不是 Display Model 半色調（2026-09-25）

- **背景**：Display Model 半色調把切到的牆也一起變灰。使用者：「平面淡化可以，但建築外輪廓要清楚，剖面也是」。
- **決策**：Display Model 維持一般；主要構件剖切線黑、投影線中灰，其他模型類別半色調，外牆（帷幕牆或類型功能＝外牆）元素取代加粗。
- **理由**：API 的半色調是整個元素一起淡，無法只淡投影線；用顏色與線寬模擬。
- **後果**：外牆判定只看牆類型的「功能」參數，類型設錯會判錯。

## D-017 ③ 底圖用確定性暫存複本匯出，並與 DPI 脫鉤（2026-09-24）

- **背景**：標記在底圖上系統性偏移。先修註記裁剪外擴（推測），仍不準；後來查到 PNG 帶 150 DPI，`Stretch.None` 讓底圖縮成 64%。
- **決策**：匯出前建立去樣板、矩形裁剪、最小註記外擴、隱藏外伸註記的暫存複本，匯出後回滾；`ImageBrush.Stretch=Fill`。
- **理由**：讓匯出範圍只剩兩種可能並用長寬比判定，不再猜；DPI 問題從根本排除。
- **後果**：每次換底圖都要開一個 TransactionGroup（會回滾，不留復原紀錄）。

## D-018 底圖挑選共用步驟 0–4，放置平面優先（2026-09-25 第二版）

- **背景**：「依名稱第一張」挑到只有 8.3×16.7 m 的放大平面；Snowdon Towers 一樓由多個高程相近的樓層組成，相機所在樓層的平面都不含相機。
- **決策**：所有自動挑底圖的入口共用 `BaseMapPlanChooser.Choose`：放置平面 → 同層包含 → ±1.5 m 樓層包含 → 下方樓層包含 → 同層最大。
- **理由**：Revit 不記相機是在哪張平面放的，所以放置時自己用 ES 記；其後依「包含相機」優先。
- **後果**：舊相機沒有放置紀錄，走步驟 1 以後。

## D-019 相機標記先做 B 型（註解），A 型族群延後（2026-09-24）

- **背景**：規格原本 A（模型族群，可在 3D 看到）與 B（每張視圖的註解）都要做。
- **決策**：先做 B 型；A 型留到 Wave 2。扇形填滿 90% 透明並送到詳圖最底層。
- **理由**：B 型不會被算圖（Enscape）或數量表誤算，實作風險低；詳圖元素一定畫在模型之上，只能靠透明度與順序降低遮擋。
- **後果**：3D 等角視圖沒有相機標記。

## D-020 樓層判定只認「建築樓層」（2026-09-25）

- **背景**：模型中有很多非樓層用途的 Level（TOS、切面參考等），相機被判到錯的「樓層」。
- **決策**：只認 `LEVEL_IS_BUILDING_STORY`＝是；一個都沒勾才退回全部。清單、地圖跟隨、Key Plan 共用 `CameraMath.GetStoreyLevelsSorted`。
- **理由**：Building Story 是 Revit 本身的「這是樓層」旗標。
- **後果**：專案若沒整理這個旗標，行為退回舊規則。

## D-021 並排後以 Idling 等視窗穩定才 ZoomToFit；透視圖防護式（2026-09-24）

- **背景**：`TileViews` 要等 ExternalEvent 結束才改視窗大小，同一事件內 ZoomToFit 無效；API 文件沒說 ZoomToFit 會不會移動透視相機。
- **決策**：記下各視窗矩形，Idling 等大小變動且連續兩個 tick 相同再縮放；透視圖前後比對方位，有變就還原並停用。
- **理由**：不依賴未查證的行為。
- **後果**：並排後有短暫延遲才縮放。

## D-022 不以暫時元素模擬「顯示相機」（2026-09-24）

- **背景**：Project Browser 右鍵「顯示相機」在平面上的效果，查無公開 API 或 Postable Command。
- **決策**：跳過，不用暫時模型元素假裝。
- **理由**：假元素會污染模型、行為也不同。
- **後果**：平面上看相機靠 Key Plan 標記與 ③ 位置圖。

## D-023 用 MCP 測試工具暴露同一套服務程式碼（2026-09-25，Wave 1）

- **背景**：每一輪修改都要使用者手動點面板才能驗證，回饋慢；多數行為其實在不含 WPF 的服務層。
- **決策**：新增 5 個 MCP 工具（`list_cameras`、`run_camera_keyplan`、`set_camera_pose`、`copy_camera_to_level`、`get_view_extents`），直接呼叫面板用的服務方法；面板內原本的並排與編輯組裝移到服務層共用。工具走 MCP 既有 ExternalEvent，不經面板佇列。
- **理由**：AI 可以先自測範圍、判定與交易結果，使用者只測手感與畫面。
- **後果**：MCP 工具數 212 → 217；服務層方法成為兩個呼叫端的契約，改動要兩邊一起驗證。與 D-001 不衝突：面板仍是主要介面，工具是測試通道。

## D-024 預覽只保留獨立視窗，移除面板內嵌 PreviewControl（2026-09-24）

- **背景**：面板內嵌 `PreviewControl` 是實驗、未驗證能否嵌入停靠面板；拿掉分頁後也沒位置放。
- **決策**：只保留獨立無模式預覽視窗，並集中追蹤、在文件／Revit 關閉時強制關閉。
- **理由**：保證能動、降低維護面；避免 PreviewControl 留給 GC 在 finalizer 執行緒收尾。
- **後果**：預覽要另開視窗。

## D-025 視野扇形用非對稱四邊界角，朝前箭頭改眼睛楔形（2026-09-25）

- **背景**：使用者只拖透視裁剪框一邊時視錐不對稱（實機 log：左 −44°、右 +25°），對稱扇形與 Revit 自己的視錐線對不上；舊 FOV 讀取因深度正負號錯誤一律回 null。
- **決策**：`ComputePerspectiveFov` 回傳左／右／下／上帶號邊界角；平面、剖面、③ 扇形都用它；箭頭改成沿同兩條邊界張開的實心楔形。
- **理由**：標記要與 Revit 畫面一致。
- **後果**：俯仰不為 0 時，平面扇形與 Revit 視錐線的投影有小差異（未實機比對）。

## D-026 A 型相機標記：族群在程式內建立；視野扇形用 DirectShape；透視圖以子類別隱藏（2026-09-25，Wave 2）

- **背景**：B 型標記只存在 Key Plan 視圖，3D 與一般平面／剖面看不到相機（D-019 後果）。A 型要一個「模型族群」，並希望扇形由視野角／遠裁剪參數驅動；同時相機自己不能拍到標記。
- **決策**：
  1. 族群「RevitMCP 相機標記」第一次需要時由程式建立：依執行中 Revit 版本找一般模型樣板（`English\Generic Model.rft`，找不到試 `Metric Generic Model.rft` 等變體），加子類別「相機標記」、實例參數（視野角左／右、遠裁剪、俯仰角、相機名稱）、相機體與視線箭頭擠出，存暫存 .rfa 後載入。找不到樣板就回報並略過 A，B 不受影響。
  2. 參數化扇形不做在族群裡：視野角參數只當資料（標籤／明細表），扇形幾何改為每台相機一個 `DirectShape`（一般模型、幾何指定子類別「相機標記」的 GraphicsStyle），同步時整個重建形狀。
  3. 族群非工作平面，不能依俯仰角傾斜：一律水平，俯仰角寫進參數。
  4. 所有透視圖以類別可見性隱藏子類別「相機標記」（實例與扇形都在這個子類別）；Enscape 是否也排除交給使用者實測。
- **理由**：參數驅動的扇形需要參考線＋角度標註＋鎖定的參數化草圖，無實機可測時失敗機率高，一旦族群建立失敗整個 A 型就不能用；DirectShape 能精確畫出非對稱視錐、與 Key Plan 扇形同一套數字。用子類別統一控制可見性，比每張透視圖逐元素隱藏好維護。
- **後果**：每台相機兩個模型元素（實例＋DirectShape，扇形已釘選）；A 型會出現在 3D、數量表與算圖中（使用者自選）。視圖樣板控制 V/G 的透視圖無法隱藏，只記 log。要真正的參數化扇形，需另開一輪並實機驗證。

## D-027 反向同步（拖標記 → 相機）只支援 A 型族群實例（2026-09-25，Wave 2）

- **背景**：使用者希望在平面／剖面上拖相機標記，相機跟著動。
- **決策**：只處理 A 型族群實例被移動／旋轉：眼睛 XY＝實例位置、水平角＝實例旋轉，離樓板高度與俯仰角不變；交易「由標記更新相機」、500ms 去抖。B 型不支援。
- **理由**：B 型標記是十幾個獨立的詳圖線與填滿區域，沒有群組，使用者無法把它們當一個單位拖曳；硬猜「哪條線被拖了」不可靠。A 型實例有單一的位置與旋轉，可以直接換算。
- **後果**：要拖標記調相機，得把 ⋯ 相機標記切到 A 或 A+B。「由標記更新相機」**不**列入 DocumentChanged 忽略名單，相機改完 B 標記照常重畫；A 實例那時已在正確位置（差 < 1 mm／0.1° 不動），不會形成迴圈。面板沒按過「重新整理」時不做反向同步。

## D-028 樓層總覽沿用底圖挑選器與 B 型標記，以樓層為 ES 鍵（2026-09-25，Wave 2）

- **背景**：需要一張「這層所有相機在哪」的可列印平面。
- **決策**：一層一張 `Key Plan-總覽-<樓層名>`；來源平面用 ③ 位置圖同一個 `BaseMapPlanChooser`（排除本工具自建視圖）；ES 沿用 `CameraKeyPlanLink`，Role＝Overview、`CameraUniqueId` 欄位存 Level UniqueId；總覽一律畫 B 型標記＋名稱，與 ⋯ 相機標記設定無關；每次更新先清掉整張視圖的相機標記再重畫。
- **理由**：與 ③ 看到的底圖一致；不新增 Schema（D-005 後果）；整張重畫讓刪除或換樓層的相機不殘留。
- **後果**：`CameraUniqueId` 欄位在 Role＝Overview 時語意是樓層；讀 ES 的程式必須先看 Role。總覽裁剪只在「更新樓層總覽」／一鍵 4 視圖時重算，相機移動只重畫標記。

## D-029 一鍵出圖紙：固定版面、只移視埠不改比例、ES 認領自己的圖紙（2026-09-25，Wave 3）

- **背景**：每台相機要手動建圖紙、拖 4 個視埠；自動排版若同時改比例，會破壞一鍵 4 視圖已挑好的比例（§10.7）。一張視圖只能在一張圖紙上，使用者可能已把 Key Plan 排到自己的圖紙。
- **決策**：
  1. 一台相機一張圖紙「Key Plan-<相機名>」，以 ES（`CameraKeyPlanLink`，Role＝Sheet）認領；**不**以名稱比對接管既有圖紙。
  2. 可繪區＝圖框實例外接框內縮 15 mm（本機設定）；版面固定：左 60% 放透視圖，右欄三等分由上而下放平面／剖面／等角，視埠置中於格子。
  3. 只調整視埠位置，不改任何比例；放不下只回報 Overflow。
  4. 圖框：指定 → 面板設定 → 專案最常用 → 第一個；視埠類型：沿用最常用、顯示標題的既有類型，不新建。
  5. 視圖已在本相機圖紙上＝保留原位；在其他圖紙上＝略過並回報。（透視圖例外：改放出圖用透視複本，見 D-032）
- **理由**：比例是 Key Plan 表現法的一部分（自動挑 1:50～1:200 以放進 A3），在出圖這一步再改會兩處打架；位置可預測、使用者之後手動微調不會被重跑蓋掉。ES 認領與 D-005 同一套機制，不會誤動使用者的圖紙。
- **後果**：外接框不扣除圖框標題欄，標題欄在右側的圖框，右欄視埠可能壓到標題欄（使用者實測）；`VIEWPORT_ATTR_SHOW_LABEL` 的整數對應未查證，判斷先看顯示字串。版面比例（60%／三等分）目前是常數，需要時再開設定。

## D-030 視角版本存成相機 View3D 上的單一 JSON 字串 ES 欄位（2026-09-25，Wave 3）

- **背景**：使用者要「儲存視角並取名（A 案）、可切回、同事開檔也能用」（roadmap Wave 3）。內容是多個向量與一個裁剪框；D-015 曾因 double 欄位沒設單位讓 `SchemaBuilder.Finish()` 失敗、整筆交易回滾。
- **決策**：新 Schema `RevitMCP_CameraViewVersions`（GUID `A8D12364-5CAE-46E8-9548-41728EC43746`），只有一個 string 欄位 `VersionsJson`，內容是 JSON 陣列（名稱、時間、眼睛、前方向、上方向、裁剪框啟用、裁剪框 Min/Max＋Transform、遠裁剪距離與啟用；長度 feet）。貼在相機 View3D 上。還原是一個交易「還原相機視角：<名稱>」，儲存／刪除只動 ES。
- **理由**：單一 string 欄位沒有單位問題；版本數量可變（ES 的 array 欄位也能做，但每個分量都要一個帶 Spec 的欄位）；之後增加內容（例如視覺型式）只要加 JSON 鍵，不必換 GUID（D-005 後果：已發佈的欄位定義不可改）。存在相機上，相機被刪除時版本一起消失，不留孤兒。
- **後果**：ES 內容不可在 Revit UI 直接看見／編輯；JSON 解析失敗時視為沒有版本（只記 log）。還原後 Key Plan 範圍不自動重算（只重畫標記，同 §11.4）。

## D-031 室內相機的樓層＝眼睛所在房間的 Level；房間以輪廓＋垂直範圍搜尋（2026-09-25，MCP 自測後）

- **背景**：Revit 2024 MCP 自測（公開範例 Snowdon Towers）發現三台室內相機被判成室外：眼睛比房間底低 150 mm（相機放在另一個 Level）、閣樓相機略高於房間上限、大廳相機；另一台室內相機的樓層被判成「Block 37 - Parapet」——該模型把女兒牆 Level 勾成 Building Story，D-020「只認建築樓層」擋不住。舊的 `GetRoomAtPoint` 只試「眼睛高度／下方樓層 +1 m／+0.3 m」三個點，都依賴「下方建築樓層」判對。
- **決策**：
  1. 房間搜尋改為：同 Phase 已放置房間 → BoundingBox XY 前篩 → 邊界多邊形點在內判定 → 垂直範圍 [底, 頂] 含眼睛者優先，否則取垂直距離 ≤ 2.0 m 最近者；同 Phase 無候選時不分 Phase 再找一次。
  2. 室內相機的樓層＝房間的 Level（`room.LevelId`），離樓板高度以它計算；室外維持 D-020。套用點在 `CameraMath.ComputeGeometry`，所有功能（清單、位置圖、Key Plan、總覽分組、A 標記、人視高、複製相機、`get_camera_info`）同源。
- **理由**：房間本身就記錄了「這台相機屬於哪一層」，比從眼睛高程往下找 Level 可靠；2.0 m 容差涵蓋相機放在相鄰 Level、閣樓略高於上限等常見偏差，又不會跨到上下層的房間（樓高通常 > 2 m 以上且上下層房間會先以「範圍內」勝出）。
- **後果**：房間的 Level 可能不是建築樓層 → 清單樓層下拉、樓層總覽 `all=true` 都要補列這些 Level；`get_camera_info` 欄位不變但值會變。每次計算幾何都跑一次房間搜尋（有 BoundingBox 前篩；大模型效能未實測）。

## D-032 透視圖已在別張圖紙上時，出圖改放「出圖用透視複本」並持續同步（2026-09-25，MCP 自測後）

- **背景**：實案常把相機排在自己的 3D 圖紙上；D-029 規則 5「在其他圖紙上的視圖略過」讓一鍵出圖紙最重要的透視圖缺席（自測：「已在其他圖紙「A903 - 3D Views」上」）。
- **決策**：原相機已在別張圖紙上 → `View3D.Duplicate(ViewDuplicateOption.Duplicate)` 建立 `<相機名>-Key Plan 圖紙`，ES Role＝`PerspectiveForSheet`，放到相機圖紙；已有複本就沿用。複本在每次出圖與去抖「更新相機標記」時同步原相機的方向、裁剪框、遠裁剪。複本不是相機，所有相機清單／總覽／A 標記／新相機偵測都排除。
- **理由**：不動使用者既有的 3D 圖紙；同步讓複本永遠與原相機一致，使用者只需要調原相機。
- **後果**：專案多一張透視視圖，平面上也會多一個相機圖示（複本本身是相機視圖）；複本的視覺型式、可見性等「非幾何」設定只在建立時從原相機複製，之後不同步。

## D-033 透視圖由視圖樣板控制 V/G 時，在樣板上隱藏「相機標記」子類別（2026-09-25，MCP 自測第二輪）

- **背景**：自測 log：16 張透視圖「不可隱藏」相機標記子類別——例如套了「Architectural Presentation 3D (No Shadows)」樣板的透視圖，樣板控制模型 V/G，`View.SetCategoryHidden` 無效，A 標記與扇形出現在相機自己的畫面與出圖用透視複本上。
- **決策**：視圖本身不能隱藏、且有視圖樣板時，改在該樣板上 `SetCategoryHidden(相機標記子類別)`；只動本工具建立的子類別，樣板名稱記 log／`AMarkerLog`。出圖用透視複本建立／同步後也跑同一段。
- **理由**：相機永遠不該看到自己的標記；子類別是本工具專屬的，隱藏它不影響樣板對其他類別的控制，也不需要解除樣板（解除會改變使用者的出圖表現）。
- **後果**：使用者的視圖樣板被改了一個子類別可見性（可復原；交易「更新相機 A 標記」）；套同一樣板的正交 3D 視圖也看不到 A 標記——這些視圖多半是表現用 3D，可接受。

## D-034 一鍵出圖紙改為自動排版：扣標題欄、Key Plan 自動挑比例、透視複本等比放大（2026-09-25，MCP 自測第二輪；修改 D-029 規則 3）

- **背景**：自測圖紙：右欄壓到圖框標題欄；透視圖視埠 209×120 mm 放在 619×732 mm 的格子裡，太小；平面視埠超出格子。D-029「只移位置、不改比例」把排版全部留給使用者。
- **決策**：可繪區扣除以圖框幾何偵測到的標題欄（偵測不到＝橫式保留右側 20 %，本機可調）；透視圖左 55 %，右欄列高依內容長寬比分配；本工具的 Key Plan 視圖挑放得進格子的最細標準比例（1:20–1:200，放不進再延伸）；出圖用透視複本等比放大裁剪框填滿格子約 90 %，以 `ComputePerspectiveFov` 讀回驗證 FOV 不變，不符就還原。已在本相機圖紙上的視埠每次重新排版。
- **理由**：Key Plan 視圖與透視複本都是本工具產生、專供這張圖紙用的，調它們的比例／裁剪框不會動到使用者的東西；原相機（使用者的）裁剪框不動。等比放大裁剪框不改變透視畫面內容（FOV 相同），只改圖紙上的大小。
- **後果**：重跑一鍵出圖紙會覆蓋使用者對本相機圖紙的手動排版與 Key Plan 比例；標題欄偵測是啟發式（長直線），特殊圖框可能誤判——判定寫在 `DrawAreaSource`，必要時調 `SheetReservedStripFraction`。透視複本放大方式（X/Y/Z 或 X/Y）哪個被 Revit 接受未實機驗證。

## D-035 圖紙透視格依「實際視埠寬」決定，其餘寬度給 Key Plan；右側版面自動選（2026-09-26，MCP 自測第三輪；修改 D-034 版面）

- **背景**：MCP 實測證實出圖用透視複本**不能**以等比放大裁剪框放大（FOV 64°→101°，已讀回還原），但 D-034 仍把可繪區 55 % 保留給透視圖 → 圖紙約 40 % 空白，Key Plan 平面／剖面／等角被迫 1:75。
- **決策**：先處理透視圖（仍試放大、失敗還原），讀回實際視埠寬，透視格＝實際寬＋間距（夾在可繪寬 20–70 %），其餘寬度全給右側；右側試單欄／上二下一（40/50/60 %）／2×2，各自挑最細比例，取「最粗比例最小、再比例和最小」者。圖紙上透視圖大小由使用者在 Revit 以「裁剪區域大小 → 縮放（鎖定比例）」手動調整，面板完成訊息提示。
- **理由**：透視圖大小是程式改不動的已知量，把它當固定值來分配空間，右側 Key Plan 才能拿到剩下的全部面積、挑到更細的比例。
- **後果**：版面每次重跑會依內容重新選；使用者手動把透視圖放大後重跑，透視格會跟著變寬、右側變窄。三種版面的實際觀感待 MCP／使用者實測。

## D-036 樓層總覽：裁剪與畫扇形共用同一個半徑函式，並以讀回的標記外接框兜底（2026-09-26，MCP 自測第三輪）

- **背景**：`Key Plan-總覽-L3` 的「Unit 302 - Toward Interior」扇形超出裁剪下緣。程式碼中裁剪與畫扇形都用 `cp.FanRadiusFeet`，靜態閱讀找不到差異。
- **決策**：兩處改呼叫同一個 `OverviewFanRadiusFeet(cp)`，每台相機的半徑寫進 `ExtentsMode`；畫完標記後以 `OwnedByView` 讀回室內相機 B 標記（MarkerPlan／MarkerName）的外接框，超出裁剪（含 3 m）就外擴並列警告。
- **理由**：與其推測差異來源，不如以「實際畫出的東西」為準——無論原因為何，裁剪都包得住扇形，且 log 會記下是否發生外擴，下次能反查原因。
- **後果**：室外相機扇形仍刻意不撐大總覽（D-028 規則不變）。根因未確認：若複測時出現「已外擴」警告，看 `ExtentsMode` 的半徑與讀回框追查。

## D-037 更新既有 Key Plan 剖面：先移動／旋轉 viewer，再在讀回座標系設範圍；不行才刪除重建（2026-09-26，MCP 自測第三輪，修回歸）

- **背景**：既有 `ViewSection` 設 `CropBox`（帶新 Transform）時 Revit 只套用 Min/Max、保留舊 Transform——剖面內容跑到錯的位置（世界 Z 2111–7523、鄰近樓梯核與下層）。第一次建立時 `CreateSection` 會採用 Transform，所以只在更新時出錯。
- **決策**：更新路徑先以 `ElementTransformUtils.RotateElement`（繞目前原點鉛直軸）／`MoveElement`（水平）移動剖面的 viewer，Regenerate 後讀回實際 Transform，在該座標系算區域範圍再設 CropBox；後檢意圖與讀回的世界範圍（> 5 mm 警告），寫進 `Decisions.SectionApplyLog`／`SectionExtentDeviationMm`。找不到 viewer、方向仍不符或偏差過大 → 不在圖紙上才刪除重建；在圖紙上則不動並警告。
- **理由**：移動 viewer 保留視圖 Id（圖紙、使用者對剖面的其他設定不受影響）；刪除重建只當退路，且不能破壞已放上圖紙的視圖。
- **後果**：「移動 viewer 會帶動剖面」在 R24 未實機驗證（依 Revit 慣例與 API 文件推定）；若實測不成立，退路是刪除重建（新 Id），圖紙上的剖面則需手動處理。刪除重建時若該剖面正開在 Revit 視窗中可能失敗，會列警告。

## D-038 等角 Key Plan 切掉觀看者側兩道牆（dollhouse cutaway）（2026-09-26，使用者要求）

- **背景**：等角是從房間的一角往下看，四面剖面框都是房間 +0.6 m，最靠近觀看者的兩道牆（例：電梯側那道）擋在觀看者與室內之間，看不到室內。
- **決策**：室內相機的等角 forward＝(sx, sy, −1)/√3（sx, sy＝±1），觀看者在 −sx／−sy 側 → 近側 X 面＝sx > 0 ? MinX : MaxX、近側 Y 面＝sy > 0 ? MinY : MaxY，這兩面改為眼睛所在房間邊界線外接框（平面、軸向）往內 100 mm；遠側兩面維持房間 +0.6 m；Z 不變。預設切掉，④ ▾「等角近側牆：切掉（預設）／保留」持久化，`run_camera_keyplan` 加 `isoNearWalls`（cut／keep）單次覆寫。室外相機不變。
- **理由**：房間邊界就是牆內面，往內 100 mm 保證整道牆（含粉刷）落在框外；遠側兩道牆保留，當作室內的背景與方位參照——這是建築表現常用的 dollhouse 剖切。只用軸向外接框：與等角四角方向一致，非矩形房間也不需逐段判斷。
- **後果**：斜向或非矩形房間，近側可能切到房間本身的一小角，或留下部分斜牆；房間邊界外接框只取邊界點（不含「最近房間」fallback 為含眼睛而外擴的部分），眼睛在房間外 ≤1.5 m 時眼睛本身可能落在框外（等角不畫相機標記，不影響）。未在 Revit 內實機驗證。

## D-041 相機變動後改為「增量更新」＋快取（2026-09-26，使用者實測：A 標記模式當機、每點一個視圖卡一下）

- **背景**：log 顯示每次即時更新都重畫所有相機（「更新樓層總覽上 19 台相機的標記」「A 標記 不變 21、扇形 21」），每台約 3 秒；總覽刪標記用「視圖中所有可見元素」collector；每次快照對 21 台相機重做房間多邊形判定；每次換底圖都重新匯出。
- **決策**：①姿態雜湊（眼睛、方向、裁剪框、遠裁剪＋模型 epoch＋標記型式）與上次畫標記時相同 → 整台略過；②標記刪除改 `OwnedByView`＋`ExtensibleStorageFilter`；③總覽只清「舊樓層＋新樓層」兩張的這台相機；樓層記號只在樓層變了才重畫；「只留本相機剖面／隱藏其他 viewer」只在強制重畫時做；④A 標記只同步變了的相機，不重驗扇形樣式、沒有新放置就不重跑透視圖隱藏；⑤去抖 500 → 800 ms；⑥眼睛移動 > 300 mm 或水平角 > 5°（相對上次 Key Plan）且已有 Key Plan → 走一鍵 4 視圖更新路徑（不並排）重算範圍；⑦房間／樓層判定以「相機＋眼睛（1 mm）＋模型 epoch」快取，epoch 只在相機以外的元素變更時 +1（本工具交易不算）；⑧③ 底圖點陣以平面 Id 快取（同文件、epoch 沒變；底圖是本工具視圖時另比對本工具視圖 epoch），最多 6 張；⑨佇列中已有快照讀取時，新的快照要求合併；⑩一鍵 4 視圖：同樓層相機沒變就略過總覽；標記型式＝B（面板設定）不碰 A 標記；4 張已開著就不關閉／不重新並排，只 ZoomToFit；⑪各步驟 `⏱` 計時寫 log（`CameraPerf`）。
- **理由**：卡頓來自「全量重做」而非單一步驟；把工作量限縮到真的變了的相機與受影響的視圖，才能讓單純的點選／啟動視圖不碰交易與匯出。
- **後果**：快取以 epoch 失效，epoch 判斷若漏掉某種模型變更，房間／樓層可能用到舊結果（按「重新整理」會清底圖快取；房間快取在相機移動或任何非相機變更時就重算）。Revit 復原（Undo）本工具的標記交易後，姿態雜湊仍視為已畫——再動一下相機或切換標記型式即可重畫。未在 Revit 內量測；計時 log 留給實機量測。

## D-042 導覽監看：Idling 比對作用中透視相機的姿態（2026-09-26，使用者實測：Navigation Wheel 不觸發 DocumentChanged）

- **背景**：用 Full Navigation Wheel／繞行移動透視相機，Revit 不發 DocumentChanged，標記與 Key Plan 不會跟。
- **決策**：`Application.OnCameraManagerIdling` 對「作用中、非樣板、非出圖複本」的透視相機，每 ≥ 300 ms 讀一次姿態雜湊（只讀）；變了 → 記時間並 `SetRaiseWithoutDelay`（只在「變了、還沒停住」期間）；停住 1 秒 → 排入面板的相機更新（同 D-041 路徑），附變動前姿態（自動「A案」、移動量判斷）；更新後補一次輕量清單刷新。使用者還在動時不開任何交易；面板未啟用（沒按過重新整理）時不監看。
- **理由**：沒有 API 事件可以得知視圖相機被導覽改變，比對姿態是唯一可行作法；只讀、限頻，成本很低。
- **後果**：Idling 只有在 Revit 閒置時觸發，極短暫的停頓可能被合併成一次更新；`SetRaiseWithoutDelay` 在停住前的 1 秒內會持續觸發 Idling（CPU 較忙，之後恢復）。未在 Revit 內實機驗證。

## D-043 互動調整：單擊選取、雙擊開啟、地圖拖曳改相機；自動視角版本；停靠面板寬度無法以 API 還原（2026-09-26，使用者要求）

- **背景**：單擊名稱／標記就跑一鍵 4 視圖太容易誤觸；使用者想在 ③ 地圖直接拖相機；視角版本要自動保留原始視角；每點一次相機面板就變窄。
- **決策**：② 單擊列＝只選取（地圖高亮、需要時換到該樓層底圖、置中），**雙擊名稱**＝一鍵 4 視圖；③ 單擊標記＝選取、雙擊＝一鍵 4 視圖、雙擊空白＝符合畫面；按住「已選取」相機的圓點拖曳＝移動、Shift＋拖曳或拖視線末端把手＝旋轉，拖曳中只動 WPF 畫布，放開才送出一次編輯（與 `set_camera_pose` 同一路徑：離樓板高度與方向不變），Esc 取消。相機第一次被任何路徑修改前（清單、`set_camera_pose`、拖 A 標記、地圖拖曳、導覽、人視高）沒有版本 → 自動存「A案」；儲存建議名稱＝下一個空字母「B案」「C案」…；還原前目前視角不在任何版本裡（1 mm／0.05°）→ 自動存「自動備份 HH:mm」；版本選單新到舊、目前視角符合者打 ✓。停靠面板：Revit API 沒有讀寫「目前停靠寬度」的方法（`DockablePane` 只有 Show／Hide／IsShown，`DockablePaneState` 只是註冊時的初始狀態）→ 不能還原寬度；改為避免重複並排（D-041 ⑩）並宣告 `MinimumWidth = 300`。

## D-044 剖面轉 90°：單一相機、持久化於相機元素本身的 ES 開關（2026-09-27，使用者要求：「有時候會想看另一向的剖面」）

- **背景**：Key Plan 剖面方向（對齊房間長邊／沿視線）是面板全域設定，套用到所有相機；使用者有時對「同一台相機」想看垂直於目前方向的另一向剖面，不想為了單一相機去改全域設定（會影響其他相機下次重算）。
- **決策**：新增第三個 ES Schema `RevitMCP_CameraSectionOptions`（GUID `A50006E7-15DF-4114-9032-904C391CD569`，欄位 `SectionRotate90: bool`），記在**相機元素本身**（不是剖面視圖、也不是面板設定），預設 false、跨 session／同一份 .rvt 給同事看到的值一致。`ComputeSectionSpec` 在既有模式（對齊房間長邊／沿視線，含房間長軸模式把原點移到中心線那一步）決定好軸與水平範圍之後、`anchor=Camera` 區塊（原點改回眼睛、看向側翻轉、深度）之前，若這台相機的開關為真，呼叫新方法 `ApplyRotate90`：把軸繞垂直軸（`XYZ.BasisZ.CrossProduct(axis)`）轉 90°，水平範圍沿新軸重新投影——室內用眼睛所在房間頂點 ±0.6 m buffer（與其他規則同一個 buffer 常數），室外／無房間用等角 XY 範圍（房間外接框+buffer 或扇形外接框）投影；深度重置為 NaN 交回既有預設（`anchor=Camera` 會整個覆蓋，只影響 `anchor=Center`＋房間長軸這個組合）。之後 `anchor=Camera` 區塊與 `ClampSectionSpecToPlanCrop` 原樣對「已轉向」的 spec 運作，不需要另外改。UI：右鍵選單與④下拉（作用在目前選取相機、沒選取停用）各一個可勾選項目「剖面轉 90°（另一向）」，切換時先寫 ES（單一小交易「剖面轉90°」），成功後照「重設剖面位置」路徑（`forceResetSection=true`）立即重建，讓效果馬上看得到。MCP `run_camera_keyplan` 新增 `sectionRotate90`（布林）：有給值就設定並持久化這台相機的開關、且強制這次重設剖面；`list_cameras` 回報於 `SectionOrientation.Rotate90`。
- **理由**：存在相機元素本身而不是剖面視圖，是因為剖面視圖可能還沒建立（第一次跑一鍵 4 視圖前）就想先設定；不做成單次覆寫（如 MCP 既有的 `sectionMode`/`sectionAnchor` 單次參數）是因為這是使用者對「這台相機」的長期偏好，不是一次性測試參數。`HasUserMovedSection` 比對的是「上次程式產生時讀回存的實際 CropBox 狀態」而不是重新計算的 spec，所以正常情況下（沒有手動調整）下次執行即使不強制重設也不會被誤判為手動移過；仍在切換當下強制重設，確保使用者立刻看到效果，不必等下一次一鍵 4 視圖。
- **後果**：`anchor=Center`＋房間長軸＋轉 90° 這個組合，深度改用預設 ±1.5 m（不是原本沿舊視線方向算出來的深度），是刻意簡化、未經實機視覺驗證是否好看；沒有房間也沒有等角 XY 資料時退回扇形半徑 fallback，範圍可能偏保守。只加了 C# 服務層／UI／MCP 參數，未新增 Runtime MCP 工具（維持 221）。未在 Revit 內實機驗證。

## D-045 D-044 修正：轉 90° 後深度改用房間投影範圍；剖面看向與視線同向時只畫眼睛圓圈（2026-09-27，MCP 實機測試後）

- **背景**：D-044 上線後 MCP 實機測試（Snowdon Towers 樣例）。室外相機（沿視線模式）轉 90° 完全正確：軸垂直於視線、剖切面通過眼睛、方向朝前，平面看得到通過眼睛的虛線剖面線，轉回 0° 用既有剖面更新路徑正確復原（0° 誤差、視圖 id 不變）。室內相機「Camera at Kitchen 01」（對齊房間長邊模式）轉 90° 後方向正確（軸 (0,1)，剖切面通過眼睛，朝相機那一側看），但發現兩個問題：(1) 深度只有 1.5 m（`anchor=Camera` 原本一律用「扇形半徑」當深度），轉 90° 後剖面沿房間長軸（約 10.2 m）看，1.5 m 深只看到近側牆／衛浴固定物，看不到房間內部；(2) 剖面裡的側視垂直扇形（紅色楔形，代表相機垂直視野）在這個方向下等於「順著視線看下去」而非真的側視，畫出來會誤導。
- **決策**：
  1. **深度**（`ComputeSectionSpec` 的 `anchor=Camera` 區塊）：`rotate90` 且找得到眼睛所在房間時，深度＝`max(原深度＝扇形半徑, 房間頂點沿「翻轉之後最終看向」投影範圍 + 0.6 m buffer)`；室外／無房間維持舊規則（扇形半徑）。「翻轉之後最終看向」＝用 flip 後的最終軸重算 `up × axis`，不能直接用 flip 前的 `look` 變數（方向可能已經反過來）。深度只在這一處公式改，`CreateSectionFromBox`（新建）與 `UpdateExistingSectionFrame`／`SetSectionFarClip`（更新既有剖面）都是從同一個 `spec`／意圖框讀 Z 範圍，兩條路徑自動一起生效，不必分別改。
  2. **側視扇形抑制**（`DrawSectionMarker`）：新增幾何判斷——剖面「看向」（−BasisZ）與相機水平視線夾角 < 45°（新常數 `SectionFanSuppressAlongSightDeg`）時，只畫眼睛圓圈，不畫垂直扇形／楔形；判斷只看幾何角度、不看是否轉 90°，所以任何其他配置只要剖面恰好看向視線也會正確套用。平面視圖的扇形不受影響（維持既有的原本邏輯）。
- **理由**：深度用「扇形半徑」的前提是剖面大致沿視線方向（扇形半徑本來就是「視線離開房間的距離」），轉 90° 後這個前提不成立，改用轉向後真正會看到的房間深度更合理；判斷側視扇形要不要畫改用幾何角度而非 rotate90 旗標，是因為造成「順著視線看」的組合不只轉 90° 這一種（理論上其他模式／設定組合也可能湊出接近的方向），幾何判斷才能通用覆蓋。
- **後果**：深度改用房間投影後，室內＋轉 90°＋房間很深的相機，剖面深度會明顯變大（例如本例 10.2 m），沿深度方向的其他元素（樑、設備）會被剖進來更多，這是刻意行為（看得到房間內部）但未經視覺驗收「好不好看」；45° 的抑制門檻是估計值，未查證是否所有斜角組合都適用，只在極端案例（室外沿視線、室內對齊房間長邊各一台）驗證過方向與深度正確，尚未針對「側視扇形抑制」重跑 MCP 複測。本輪修正沒有再部署、沒有再跑 MCP，留給下一輪。

## D-046 沿視線看的剖面自動跳過眼前的牆（2026-09-28，使用者決策，MCP 實機測試後）

- **背景**：D-045 上線、部署、MCP 複測後（commit `2b4baf4`）：室內剖面轉 90° 深度已修正為 11132 mm、側視扇形已正確抑制（只畫眼睛圓圈）。但「Camera at Kitchen 01」站在門邊、緊貼著牆（眼睛 X=-19665 mm；廚房東側牆＋門就在看向方向前方約 150–300 mm 處）——剖切面通過眼睛時，沿視線看的剖面只切到那道牆（牆上的衛浴固定物），房間本身被擋住看不見。使用者拍板：**自動跳過相機正前方的牆**。
- **決策**：只在「沿視線看」（與 D-045 的側視扇形抑制共用同一個幾何判斷：剖面最終看向 `lookFinal` 與相機水平視線 `center` 夾角 < `SectionFanSuppressAlongSightDeg`＝45°）才套用；側視剖面（預設模式）不受影響，剖切面仍通過眼睛。判斷式成立時，新增 `ComputeWallSkipOffset`：從眼睛沿 `lookFinal` 打水平射線（`ReferenceIntersector`，沿用 `FindRaycastView` 站立面射線同一張非透視／非樣板 3D 視圖、`FindReferencesInRevitLinks=true` 含連結模型），目標類別牆／門／窗／帷幕嵌板（帷幕牆本身即 `OST_Walls`）；只認眼睛前方 1.5 m（`WallSkipTightRangeMm`）內的最近命中，更遠的牆視為場景一部分不處理。找到最近命中後，在同一條射線所有命中裡找「同一元素」（比對 `Reference.ElementId`＋`LinkedElementId`）中 Proximity 最大者當「元素背面」（夾一個合理厚度上限 `WallSkipThicknessSanityCapMm`＝1.5 m，避免抓到牆後面另一片牆），剖切面挪到背面再 +100 mm（`WallSkipClearanceMm`）。遠裁剪維持在原世界位置（深度＝原深度 − 位移量，設下限 0.5 m 避免深度歸零/負值）；剖面原點沿 `lookFinal` 前移對應距離，X 範圍（沿軸向）與垂直範圍不受影響（`lookFinal` 與軸、與世界 Z 都垂直，純水平深度方向位移）。`ClampSectionSpecToPlanCrop` 與 `UpdateExistingSectionFrame` 讀的都是通用的 `spec.Origin`／意圖框，本來就不假設原點＝眼睛，確認不需要另外改。`DrawSectionMarker` 新增：眼睛投影點換算到剖面 `CropBox` 本機座標，落在裁剪框 X/Y 範圍外（剖切面前移後眼睛可能被推到裁剪框「相機背後」那一側）就整個標記略過、不拋例外。
- **理由**：跳牆判斷復用「看向與視線同向」的幾何測試，而不是另外綁 `rotate90` 旗標，理由與 D-045 相同——會造成這個方向組合的不只轉 90° 一種；1.5 m 的緊貼門檻與 100 mm 的餘量是估計值，取「站在門框/牆邊」這種明確場景，避免誤傷「房間對面本來就有一道牆」這種正常構圖（那道牆通常 > 1.5 m）。
- **後果**：牆背面判定用射線命中分組（同一 `ElementId`＋`LinkedElementId` 內取最大 Proximity），對於複合牆（多層構造）大致等於牆的總厚度，但夾了 1.5 m 的合理上限，異常厚的牆（或射線斜穿多片牆時被誤判為同一元素連續命中）可能被低估背面距離；連結模型內的牆只做「有沒有偵測到、往前挪多少」，log 不會完整解析連結內元素的類別／名稱（與既有站立面射線 `EnsureStandingSurface` 對連結元素的簡化處理一致，未強求完整化）。剖面裁剪框外的標記略過是防禦性寫法，尚未在 Revit 內實際遇到觸發這條路徑的案例，未經視覺驗證。本輪修正只編譯與跑 QA/QC，未部署、未再跑 MCP，留給下一輪複測。
