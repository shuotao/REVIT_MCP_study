林家維（@CWLin0518） 開發綠建材 Revit 導入工具鏈時推完的 23 張看板卡，全部 stage: done， 建立於 2026-07-30 ～ 2026-08-12。 Domain 索引回答「有哪些方法」，本頁回答「這些方法是怎麼被做出來的、當初驗在哪個 TypeId 上」。 每張卡連到它的 JSON 原始檔、它催生的 domain／skill／工具，以及當時留下的實測 ID。

SECTION 01 · WHAT

什麼是看板卡

tools/kanban/cards/ 底下的 23 個 JSON 檔，一張卡一個檔。 看板頁把它們渲染成欄位視圖。 這就是林家維在分享中說的「專案看板的方式，就是那個字卡」。

它跟一般專案管理的卡不同。ai/process/kanban.md 開宗明義： 「這個看板追蹤的是『這項任務對 AI agent 來說是否可以安全執行』，不只是單純的任務狀態。」 Trello／Jira 的卡問「這件事做到哪了」；這套卡問「這件事夠不夠清楚到可以交給 AI 去動我的 Revit 模型」。

每張卡有兩組布林閘門：

  • readiness（7 項，進場門檻）：problem_clear、non_goals_clear、acceptance_testable、files_known、scope_defined、verification_contract、human_approval_recorded。不全為 true，不准交給 agent 動手。
  • gates（6 項，出場門檻）：product、ui、architecture、security、test、code_review。不全為 true，不算完成。
  • dependsOn（硬相依）：政策明定「列出的卡片全部是『完成』；只要有一張還沒完成，這張卡不能進入『Agent 執行中』」。

推進流程有 12 個欄位，每欄都寫了離場條件：

收件匣 → 待釐清 → 待產品核准 → 待 UI Mockup → 待架構規劃 → 待任務卡
    → AI 就緒 → Agent 執行中 → 待驗證 → 待審查 → 待人工驗收 → 完成

完整規範見 ai/process/kanban.md， 它連 WIP 上限都定了（「若審查欄位滿了，就停止建立新的 AI 工作」）。

SECTION 02 · 讀之前必看

卡片是歷史紀錄，不是現行方法

這 23 張卡全部是 stage: done，建立於 2026-07-30 ～ 2026-08-12。 它們記的是「那一天做了什麼、在哪個 TypeId 上驗過」，不會再更新。

而 domain 是活文件，會改版。兩者的關係是單向的： 卡片是 domain 的出生證明與證據，不是 domain 的內容來源。 方法的現況一律以 domain 為準——這是 CLAUDE.md 的既有規則（衝突時 domain 勝）。

所以真正要注意的不是「卡片改了 domain 沒跟上」（卡片不會再改），而是時間差： domain 已經前進、卡片停在原地。本頁把已知的情況以黃底標在該列上。

另一個時間差的例子不在任何卡片裡：domain/GM_parameter-schema.md 的 §6「標章效期與資料新鮮度」是 2026-08-31 才加上去的，23 張卡中沒有任何一張提到它。

SECTION 07 · 缺口

編號缺口與併卡

卡號是 TASK-001～006、008～011、013～015，加 TASK-005.1～005.8 與 005.10～005.12。 TASK-005.9、TASK-007、TASK-012 在 main 與作者的 fork 兩邊都不存在； 另有三張卡標題自帶「[已併入 TASK-005.x]」。

這對應到他在分享中自述的「我其實到後面，我其實都自己會有點亂掉了」。 看板本身收編了，但「開發到中期卡片爆炸、如何收斂」目前沒有任何 domain 或 skill 回答它—— 這是這條工具鏈唯一尚未沉澱成方法的一題。
