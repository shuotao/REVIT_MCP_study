# MEP 前期設計方法學習計畫 — 訓練紀錄檔

## 文件性質

- **類型**：專案工作紀錄（非 CLAUDE.md 定義的 canonical / redirect / command / skill 任一類；不是 AI 指令檔，是人機共讀的進度台帳）。
- **語言**：全程繁體中文。
- **更新方式**：**活文件（living document）**，與 `log/YYYY-MM.md` 的「append-only、不得改寫歷史」規則不同——本檔隨計畫推進**可重新整理既有章節**，但每次重大更新須在文末「版本更新記錄」留痕，不得無聲改寫已定案的判斷或已標記的事實來源。
- **維護角色**：本檔由「記錄員（recorder）」子任務維護，**不呼叫任何 `mcp__revit-mcp__*` 工具**、**不修改 `domain/*.md`／`CLAUDE.md`／`README`／skill／原始碼**、**不執行 git commit/push/checkout**。所有 Revit 實機數據均由主 session（人類操作者 + 主 agent）於各自 turn 實機查證後轉述給記錄員，記錄員只負責忠實記載與交叉核對，不自行發明或補全任何數值。
- **誠實原則**：本檔內每一個數字、每一個「已驗證」標記，都必須能回指一個具體證據來源（commit hash、檔案路徑+行號、或「主 session 於 YYYY-MM-DD 實機讀取」）。找不到來源的一律標記「未驗證」，不得用推測值填補。

**給年輕工程師的白話版（2026-08-11 更新，L-E 驗證後定案）**：本方法的自動化型態確定為**「骨架自動、判定手動」**。

- **骨架自動**：明細表（Schedule）本身的建立與讀回可以完全交給 MCP——`create_view_schedule {category:"Spaces"}` 建表、`read_schedule` 讀回，欄位設定（含 Space 專屬欄位如 Actual Supply Airflow）都在自動化範圍內。
- **判定手動**：但 Space 元素本身（L-A）、Tag 與需求專案參數（L-B）、計算欄位公式（L-C）、條件格式標色（L-D）這四項，仍然一律要回到 Revit UI 手動做——這不是 AI 能力不足，是 Revit API 本身在這幾個點沒有對外開放對應的設定介面。

**這個區分很重要，務必記住（見下方 Open Item 5）**：明細表骨架能自動生成，**不代表整張檢核表的「合格/不合格」判定也自動了**——那四項判定要素仍然要人工建立。本次驗證建出的表資料列是空的（因為模型沒有 Space 實例），這是正常結果，不是工具失敗。

**單位前提（2026-08-11 更正）**：`ARCH_LINK.rvt` 目前是英制。coordinator 已澄清：`Area × 係數` 被誤判為成本密度的坑**只發生在明細表的 Calculated Value 公式裡**，不影響單純讀值換算——本輪盤點的英制房間數字（68 間/13202 SF 等）可以直接換算成公制使用，不需要重讀。但**切換專案單位（`set_project_units`）的動作該發生在 MEP 自己的模型，不是 `ARCH_LINK.rvt`**——後者是建築師的交付物，機電不該去改它的專案單位設定。詳見 Open Item 4（已改寫）。

### Phase 2 之後：一律在工作副本上操作，不在原始課程／範例模型上操作

**2026-08-11 使用者裁決（完整規則見 Decision Log D10）**：從 Phase 2 開始任何需要累積狀態（手動建 Space、Tag、矩陣內容）的操作，一律在 `C:\Users\<YOUR_USERNAME>\Desktop\MEP\_work\` 底下的工作副本進行，**不得**直接在 `C:\Users\<YOUR_USERNAME>\Desktop\MEP\M1\` 的原始課程模型上做——原始模型永遠不動、永遠不存檔。

目前已建立的工作副本：

| 檔案 | 角色 | 大小 |
|---|---|---|
| `_work\WORK_M1_02_Space-Demand-Matrix.rvt` | 宿主檔（在此建 Space、Tag、矩陣） | 19,230,720 bytes |
| `_work\ARCH_LINK.rvt` | 連結檔（供宿主檔連結讀取 Room 資料） | 33,923,072 bytes |

**年輕工程師最容易踩的坑**：`_work\ARCH_LINK.rvt` **必須保持原檔名，不能跟著改成有 `WORK_` 前綴或其他辨識用命名**。Revit 的連結路徑是依檔名解析的，宿主檔 `WORK_M1_02_Space-Demand-Matrix.rvt` 內部存的連結目標就是「同資料夾下一個叫 `ARCH_LINK.rvt` 的檔案」——如果手滑把這個副本也改名（例如改成 `ARCH_LINK_copy.rvt`），Revit 開啟宿主檔時連結會直接找不到，畫面上的建築房間全部消失，而且不會有明顯的錯誤訊息提示「你改錯檔名了」，初學者很容易誤以為是別的地方壞掉。**判斷一個資料夾是不是工作副本，看的是整個 `_work\` 資料夾這一層，不是看每個檔案的檔名。**

**兩條規則不要混淆**：
1. **可以累積狀態**的操作（手動建 Space、填矩陣、跑迭代重檢）→ 一定在 `_work\` 工作副本上做。
2. **驗證某個 MCP 工具行為**（例如「這個新工具的某個參數到底吃不吃 XX」這類問題）→ 一定回到乾淨的原始模型上單獨測，**不得**在已經累積了一堆手動 Space/矩陣資料的工作副本上做，因為累積狀態會污染歸因（分不清結果是工具本身的行為，還是被之前手動改過的東西影響）。L-E 的驗證就是照這條規則、在乾淨的原始 `ARCH_LINK.rvt` 上做的（見 D6、D10）。

### Tag／§102 分類階段：MCP 與 GUI 怎麼分工（2026-08-11 實測得出，**下方為修正版，見 Decision Log D13／D21**）

⚠️ **本節第一版（D13）在 Tag 分類時驗證有效，但在後續 §102 用途類別分類時造成三起真實寫入事故（`⋯` 縮寫誤貼、`DR OFFICE` 被覆蓋、`DR SCRUB 1506` 未經判定的值），已由 D21 修正。下方直接給修正後的版本，避免年輕工程師照抄第一版踩坑。**

四類 Tag（`MEP_Tag`）與 §102 用途類別分類，**不是「能自動就全自動」，而是依資料形狀分工**：

- **同一個值要蓋很多列，且能用單一排序條件把這些列跟其他列隔離開**（例如 44 個 Space 都要標成單純 `DEMAND`，且排序後這些列彼此相鄰、不與需要不同值的列混在一起）→ 用 **Revit UI 的明細表選列 + Properties 面板**一次改。
- **少數、散落、容易挑錯的例外** → 用 **MCP 的 `modify_element_parameter`** 逐筆寫，因為「散落但已知清單」正是程式化操作的強項。
- ⚠️ **一旦排序後相鄰列需要不同的值，即使兩邊各自都是「同值多筆」，也必須用 MCP，不得用 GUI 批次選取。** 這正是 `DR OFFICE` 事故的根因：依名稱排序時 `CONSULT`→`DR OFFICE`→`EXAM` 相鄰，GUI 選取範圍不小心把 `DR OFFICE` 也掃了進去，5 筆原本正確的值被覆蓋。**「同值多筆」本身不足以判斷能不能用 GUI，還要看這批列在排序後是否真的跟其他值隔離。**

**給年輕工程師的判斷準則（修正版）**：不要只問「值是集中還是分散」，還要多問一句「**如果我照這個排序條件選取，選取範圍的頭尾會不會誤觸相鄰的、需要不同值的列？**」——會誤觸就必須用 MCP，即使目標本身是同值多筆。**這條規則本身尚未寫入 domain 或任何 skill（見 Open Item 10），目前只存在於這份訓練紀錄，讀者需自行留意，不要假設它已經是系統性防護。**

### 引用查證：人工抽查與機械全驗都不完備，合用才收斂（源自外部並行機電案，見進度台帳【事件 1】；本節已於 2026-08-12 移除案件識別細節與具體筆數）

這不是本學習計畫的 Revit 操作步驟，但方法論價值足以寫進這裡：一次文件引用查證工作做了兩層查證——人工稽核抓到一部分頁碼錯誤，另寫的機械驗證腳本抓到更多（人工有明顯漏抓），但腳本自己也產生偽陽性需要人工排除。**教訓**：無論是查證 Revit 模型資料還是查證外部文件引用，**單一方法（純人工或純機械）都會漏東西，兩種方法互相校對才會收斂**。年輕工程師在做任何「盤點／驗收」類工作時，應該預設規劃至少兩種獨立的檢查手段，而不是做完一輪人工檢查就視為完成。

### 交叉驗算的反直覺判準：零差異＝抄寫，不是驗證（本輪已讀取 domain 檔核對，`mep-space-demand-matrix.md` 第 570～580 行）

建計算欄位（例如 §102 法定通風量＝面積去單位×係數）之後，**必須用獨立方法驗算總計，不得直接採信明細表畫面上的數字**。這裡有兩層教訓：

1. **表面正常不代表數值正確。** 第一次建的公式漏算了面積，明細表外觀完全正常（每列有值、有 Grand Total），但總計比正確值小近 10 倍——錯誤值本身是個合理大小的數字，單看畫面無從察覺，必須靠外部獨立計算比對才抓得出來。
2. **驗算數值不得取自明細表本身**，否則等於拿明細表驗證明細表，兩者必然相符，驗證即失去意義，要從元素參數直接另行取值計算。**且驗算結果出現微小差異（本案約 0.01%～0.012% 量級，來自顯示精度捨入）才是正常、甚至是好現象**——這代表兩邊真的是獨立算的。**完全零差異反而該起疑：通常代表兩邊用了同一組數字，那不是驗證，是抄寫。**

給年輕工程師的操作提醒：驗算後若兩個數字完全相同到小數點最後一位，先別急著慶祝算對了，回頭檢查一下是不是不小心讓兩邊共用了同一個中間值。

### Open Item 5（新，本輪 ops 掃描）— 自動化程度提高後，「骨架完成」可能被誤讀為「檢核完成」

**問題**：L-E 解除後，`create_view_schedule {category:"Spaces"}` 一步就能建出一張看起來像模樣的 Space 明細表——有品類、有欄位（含 Actual Supply Airflow 這種專業欄位）、可以 `read_schedule` 讀回。但這張表**沒有計算欄位（L-C 仍手動）、沒有條件格式標色（L-D 仍手動）、甚至可能完全沒有 Space 實例（L-A 仍手動）**。「骨架」與「判定」之間有一道目前無法用工具跨過的落差。自動化程度低的時候，這道落差很明顯（每一步都要人動手，人自然會意識到還沒做完）；**自動化程度提高後，這道落差反而更容易被忽略**——年輕工程師看到「MCP 一鍵建出 Space 明細表」，容易誤以為整張檢核表（含合格/不合格判定）都是自動產出的，實際上這張表在 Space 實例、公式、標色都補齊之前，只是一個空殼——本次驗證的實際結果正是如此：資料列全部為空。

**這與 domain 3-3 節「得到的是一份精確的錯誤」是同一種風險的另一種型態**：3-3 節講的是「上游資料有缺陷但看起來有數字」，這裡是「骨架自動生成但看起來像完整成品」，共同結構都是「表面上的完整度掩蓋了實際上的不完整」。

**後果**：若沒有明確的檢查點提醒操作者「骨架完成 ≠ 判定完成」，年輕工程師可能把「已用 MCP 建好 Space 明細表」直接當成「逐室檢核已完成」回報給上級，跳過 L-A～L-D 這四項手動步驟，交出一張空的或不完整的表卻不自知。

**可選項**：
- (a) 在 domain 第五節或操作 SOP 裡明確加一條「骨架建立完成後的驗收檢查」——例如要求 `read_schedule` 讀回時明確核對資料列數是否等於 Space 實例數（0 代表 L-A 尚未做）、關鍵計算欄位是否存在（否則 L-C 尚未做）。**代價**：需要修改 domain 檔，超出本記錄員授權；且這個檢查本身還是要人工判讀 `read_schedule` 的輸出，不是新的自動化能力，只是多一道提醒。
- (b) 在對外溝通（教材、Phase 4 教學文件）中，把「骨架自動、判定手動」這句話當成強制的口頭禪，每次示範這個能力時都同時展示「這張表目前是空的/不完整的」，避免示範本身造成誤導。**代價**：純溝通層面的緩解，不解決工具能力落差本身，仰賴教學品質。
- (c) 不特別處理，仰賴 domain 文件裡已經寫的「骨架自動、判定手動」這句話本身足以澄清。**代價**：這句話目前只出現在 domain 內部（工程師視角的技術文件），不會出現在明細表本身或 MCP 工具的回傳訊息裡，操作當下沒有任何即時提醒，容易被略過。

**處置結果（2026-08-11 之後，本輪讀取 domain 檔核對存在）**：選項 (a) 已被實作。`domain/mep-space-demand-matrix.md` 新增「L-E 解除後新增的風險：把骨架誤當成完成品」一節（第 599～619 行），提出 6 項「完成度檢核」清單（Space 實例是否>0、覆蓋率、自建參數欄存在、計算欄位存在且有值、單位正確、條件格式已套用），並明講「工具的回傳本身不會告訴你這件事——`create_view_schedule` 回『成功建立明細表』、`read_schedule` 回一張結構正確的表，兩者都不會說『這張表還不能用』」。**第 6 項（條件格式）被明確標為硬邊界、不可機器驗證，只能人工目視並具名簽署**——這與 §3-3 節「條件格式無 API 讀寫」的既有限制一致，沒有假裝已解決不可解的部分。**本 Open Item 因此視為已處置（非已消失）**：風險本身沒有被工具能力進展抹除，但已從「無人提醒」變成「有明文清單可查核」。年輕工程師的 SOP 應直接引用這 6 項清單，不需要重新發明。
